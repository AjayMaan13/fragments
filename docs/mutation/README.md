# Mutation testing (Stryker)

Line coverage says which code the tests _run_. Mutation testing says whether the tests would _notice_ if that code were wrong: Stryker makes small changes to the source (flip `<` to `<=`, drop a condition, empty a string) and re-runs the tests. A mutant that no test fails on has **survived**, which means a behaviour nobody checks.

```bash
npm run mutation          # about 17 minutes; HTML report in reports/mutation/mutation.html
```

Config: [`stryker.conf.json`](../../stryker.conf.json). It mutates `src/convert.js`, `src/model/fragment.js`, `src/model/job.js`, `src/routes/api/*.js`, `src/worker-core.js` and `src/queue.js`, runs only the tests that cover each mutant, and is gated in CI by [`.github/workflows/mutation.yml`](../../.github/workflows/mutation.yml) (weekly and on demand, fails below 90%).

## What mutation testing found

Real defects and gaps, not just numbers:

- **A real bug.** When resizing an image failed, the 500 error was sent with `Content-Type: image/png`, because the handler set the image header before converting and `res.json` does not override an existing type. The error body was JSON labelled as an image. Fixed in `src/routes/api/getId.js`, with a regression test.
- **Untested promises.** Every API error message (a contract clients read), the exact numeric limits, the `Location` header, the JSON-to-XML wrapping rules, and which type pairs must _not_ convert had no test that would fail if they changed.
- **A subtle one in the job model:** a job that succeeded on its last attempt would have been reported "worker did not finish" if the status check lost its status guard. Now pinned by a test.

## Ignored on purpose: logging

Mutations inside `logger.*(...)` calls (the log object, the message text, or deleting the log line) cannot change what the program does, so no behavioural test can kill them. [`stryker-plugins/ignore-logger.mjs`](../../stryker-plugins/ignore-logger.mjs) tells Stryker to skip calls on `logger`, `log` and `baseLogger`. Those 117 mutants appear as "ignored" in the report and are left out of the score. Error messages in API responses are **not** ignored; they are tested.

Counting logging, the first run scored 73.54%. Ignoring it, 76.39%. Both are reported so the comparison is honest.

## Notes

- **Static mutants.** Stryker's incremental mode can reuse results for constants that run at import time (e.g. `MAX_EXPIRES_IN`) even after tests change. The reported "after" figure comes from `--force`; the CI workflow uses `--force` too.
- **Test timeout.** `jest.config.js` allows 15 s per test (was 5 s). Stryker runs the suite instrumented and in parallel, several times slower than a plain run; a passing test never gets near it.
- **Leftover sandbox.** A crashed Stryker run can leave `.stryker-tmp/`; `jest.config.js` ignores it so it can't double the test count.
